# /go — закоммитить, задокументировать, влить в main

Выполни полный цикл доставки текущей feature-ветки в `main`. Работай последовательно, не пропускай шаги. Не спрашивай подтверждений на каждый шаг — действуй, пока не упрёшься в реальный блокер (конфликты, нет remote, грязный main и т.п.).

## Предусловия

1. Убедись, что текущая ветка **не** `main`/`master`. Если ты на `main` — остановись и сообщи об этом.
2. Собери состояние: `git status`, `git diff`, `git diff --staged`, `git log -5 --oneline`, `git branch -vv`.
3. Если нечего коммитить и нечего пушить/мержить — сообщи и заверши.

## 1. Документация `docs/features`

Перед коммитами (или как отдельный логический инкремент в конце серии коммитов) обнови продуктовые docs:

1. Посмотри `docs/features/` и diff ветки относительно `main` (`git diff main...HEAD` + незакоммиченные изменения).
2. Определи **одну или несколько фич**, которые появились/изменились в этой ветке.
3. Для каждой фичи:
   - Если есть подходящий файл в `docs/features/` — **обнови** его под актуальное поведение.
   - Если нет — **создай** `docs/features/{имя-фичи}.md`. Имя файла: короткий kebab-case по сути фичи (например `text-only-export`, `optional-knife`).
4. Структура нового/обновлённого файла (ориентир — существующие docs в этой папке):
   - Заголовок и имя ветки
   - Проблема / зачем
   - Решение
   - Поведение (таблица или список)
   - Изменённые файлы
   - Как пользоваться / миграция при необходимости
   - Как проверить
5. Учти `.gitignore`: `*.md` игнорируется, кроме `README.md` и `docs/**/*.md`. Если новый doc не виден в `git status` — проверь ignore и при необходимости поправь `.gitignore`.

Документация должна попасть в коммиты этой ветки (отдельным docs-коммитом или вместе с соответствующим инкрементом — как логичнее).

## 2. Коммиты — логические продуктовые инкременты

Разбей все изменения на **отдельные коммиты**, каждый = один понятный продуктовый инкремент (не «всё подряд»).

Правила:

- Сначала спланируй группы файлов (например: CLI `--knife`; упрощение update-скриптов; смена путей; docs).
- Для каждой группы: `git add` только её файлов → `git commit`.
- Сообщения коммитов: 1–2 предложения, фокус на **зачем**, в стиле репозитория (`git log`).
- Коммит через HEREDOC:

```bash
git commit -m "$(cat <<'EOF'
Commit message here.

EOF
)"
```

- Не коммить секреты (`.env`, `*.session` и т.п.).
- Не используй `--no-verify`, не делай `amend`, не трогай git config.
- После всех коммитов: `git status` — working tree clean (кроме осознанно игнорируемого).

Если изменение одно целое — допустим один коммит. Если смешанное — обязательно несколько.

## 3. Пуш feature-ветки

```bash
git push -u origin HEAD
```

Если ветка уже tracking — достаточно `git push`.

## 4. Мерж в `main`

```bash
git checkout main
git pull origin main
git merge <feature-branch>
```

- Предпочитай обычный merge (fast-forward, если возможно).
- При конфликтах — разреши, заверши merge, не бросай репозиторий в конфликтном состоянии.
- После успешного merge переключи active branch metadata на `main`, если доступен соответствующий инструмент.

## 5. Пуш `main`

```bash
git push origin main
```

## Финал

Кратко отчитайся:

- какие коммиты созданы (hash + message);
- какие файлы в `docs/features` созданы/обновлены;
- имя запушенной ветки;
- результат merge и что `origin/main` обновлён;
- текущая ветка (`main`).

Не удаляй feature-ветку на remote, если пользователь явно не просил.
