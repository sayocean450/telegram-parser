# /start — начать задачу с новой ветки и плана

Прими описание задачи из текста **после** команды `/start` (всё, что пользователь написал вместе с вызовом). Если описания нет — спроси одной короткой фразой и остановись.

Выполни шаги строго по порядку. До аппрува плана **не пиши код** и не меняй файлы проекта (кроме создания git-ветки).

## 1. Описание задачи

1. Возьми входной текст как постановку задачи.
2. Сформулируй для себя краткую суть в 3–7 словах — она понадобится для имени ветки и заголовка плана.

## 2. Новая ветка

1. Проверь состояние: `git status`, текущая ветка.
2. Если есть незакоммиченные изменения — остановись и спроси, что делать (stash / commit / продолжить поверх). Не теряй чужую работу.
3. Предпочтительно ответвляйся от актуального `main`:
   ```bash
   git checkout main
   git pull origin main
   git checkout -b <branch-name>
   ```
   Если уже на чистой feature-ветке и пользователь явно продолжает работу там — не обязательно возвращаться на `main`, но имя новой ветки всё равно создай от текущего HEAD только если это осознанно; по умолчанию — от `main`.
4. Имя ветки: короткий **kebab-case** по сути задачи (латиница), 2–5 слов.
   - Хорошо: `optional-knife`, `text-only-export`, `fix-telegraph-fetch`
   - Плохо: `fix`, `new-branch`, длинное предложение, пробелы, кириллица
5. Переключись на ветку (`git checkout -b …`).
6. Обнови active branch metadata в UI (`SetActiveBranch`), если инструмент доступен.

## 3. Plan mode

1. Сразу после создания ветки переключись в **Plan** через `SwitchMode` (`target_mode_id: "plan"`).
   - В `explanation` укажи, что нужно согласовать план по задаче перед реализацией.
2. Исследуй репозиторий ровно настолько, чтобы план был конкретным (какие файлы/модули затронуть). Не уходи в реализацию.

## 4. План изменений

Пришли план в чат. Структура:

- **Задача** — пересказ в 1–2 предложениях
- **Ветка** — имя созданной ветки
- **Подход** — как будем решать
- **Изменения** — список конкретных файлов/компонентов и что в каждом сделать
- **Вне скоупа** — что сознательно не трогаем
- **Проверка** — как убедиться, что готово

План должен быть достаточно детальным, чтобы по аппруву можно было сразу кодить без дополнительных развилок (если развилки есть — явно перечисли варианты и рекомендацию).

## 5. Ждать аппрува

После плана **остановись и жди** явного аппрува пользователя («ок», «да», «approve», «делай», уточнённый план и т.п.).

- Пока нет аппрува — не пиши код, не коммить, не пушь.
- Если пользователь правит план — обнови план и снова жди аппрува.
- После аппрува можно переключаться в Agent и реализовывать утверждённый план (или продолжить в том режиме, куда укажет пользователь).
